# 1. 目的・位置づけ

背景（2026-08-08付）:

- 公開版（`carpoolbridge-go`）を不特定多数のチーム向けにリリースし、実利用が始まった
- 公開版はサーバーへデータを一切送らず、端末内（IndexedDB/Dexie.js）にのみ保存する設計
  （`docs/08_公開版アーキテクチャ設計.md`#1）
- 自チーム版（Firestore）も既に運用中のチームが存在する

この状態でデータ構造を後方互換なく変更すると、公開版は**サーバー側バックアップが
存在しないため復旧手段がなく**、利用者の端末内データが読めなくなる・消えるという
事故に直結する。自チーム版でも運用中データへの影響が起こりうる。

本ドキュメントは、公開後にAIが実装・提案を行う際に必ず守るべき「破壊的変更」に
関するガイドラインを定義する。`CLAUDE.md`から参照される最優先ルールの詳細版である。

---

# 2. 「破壊的変更」の定義

以下はすべて破壊的変更とみなし、3章の手順を必須とする。

- 既存フィールドの削除・型変更・必須/任意の変更
- 既存フィールドの意味（セマンティクス）の変更
  （例: `docs/08`#6の`saveCarpools`のような「upsertのみ」を「全置換」に変える等）
- Dexieスキーマ（`src/repositories/dexie/db.ts`の`stores()`定義）の変更
  （テーブル削除、インデックス変更、キー変更）
- Firestoreのドキュメント構造・コレクション名・サブコレクション位置の変更
- 既に保存されている値（IndexedDB・Firestore双方）を読めなくする変更全般

以下は破壊的変更に**当たらない**（通常の変更として進めてよい）。

- 新しいOptionalフィールドの追加（未設定時はundefined/デフォルト値として扱える）
- 新しいテーブル・コレクションの追加
- 既存データに影響しないUI・ビジネスロジックのみの変更

判断に迷う場合は、破壊的変更として扱い3章の手順に従う。

# 3. AIの行動ルール

**破壊的変更に該当する、または該当するか判断に迷う変更を行う場合、実装前に
必ず立ち止まり、以下を人間に提示して承認を待つこと。**
（`CLAUDE.md`「開発方針」の仕様変更提示ルールに準拠し、データ構造の観点で拡張したもの）

1. 問題点（なぜ変更が必要か）
2. 変更案（具体的な変更内容）
3. 影響範囲（公開版/自チーム版のどちらに影響するか、既存データはどうなるか）
4. 移行方法（マイグレーションが可能か、不可能な場合はどうするか）
5. メリット
6. デメリット・リスク

**承認なしに、既存データ構造を変更する実装を行ってはならない。**
これは`CLAUDE.md`の「AIは勝手に仕様変更しない」と同列の最優先ルールである。

# 4. 公開版（Dexie/IndexedDB）特有の注意

- バックアップが存在しないため、データ破損・消失は運営側から復旧できない
- Dexieのスキーマを変更する場合、`version()`番号を上げずに`stores()`だけ書き換えると、
  既存ユーザーの端末で読み込みエラーになる、またはテーブルが空になる
- 承認後にスキーマを変更する手順:
  1. `version()`番号を1つ上げる
  2. 新旧スキーマの差分に応じて`upgrade()`を実装し、既存データを新形式へ変換する
     （データ変換が不要な追加のみなら省略可）
  3. 既存データが入った状態からのアップグレードをブラウザ上で実際に確認する
  4. `docs/10_DexieRepository実装設計.md`のスキーマ定義を更新する

---

# 5. 自チーム版（Firestore）特有の注意

- 既に運用中のチームの本番データが対象になる
- Security Rules・型定義の変更は`main`マージ時に自動デプロイされ、即座に本番へ反映される
- 既存ドキュメントに新規必須フィールドを追加すると、追加前に作成されたドキュメントで
  そのフィールドがundefinedになり、読み取り側でエラーになりうる
- Security Rulesの変更は、意図せず他チームのデータが見える/書き込めるようにならないか
  特に慎重に確認する

---

# 6. その他、公開後に気をつけること

- Firebase Hosting（Sparkプラン）の無料枠はプロジェクト単位のため、公開版と自チーム版で
  プロジェクトを分離済み（`docs/12_公開版配布・ホスティング設計.md`#2）。今後
  新しいFirebaseリソースを追加する際も、公開版側の負荷が自チーム版に影響しない構成を維持する
- ログ（`console.log`等）に個人情報（氏名・連絡先等）を出力しない
- `main`マージ前にE2Eテスト（`npm run test:e2e`）を通す
- 公開版（`npm run build:public`）・自チーム版（`npm run build`）の両方のビルドが
  壊れていないか確認する
