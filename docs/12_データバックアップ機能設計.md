# データバックアップ機能設計

Version: 0.1

---

# 1. 目的・背景

公開版はサーバーへデータを一切送らず端末内（IndexedDB/Dexie）にのみ保存する設計
（`08_公開版アーキテクチャ設計.md`）のため、機種変更・配車担当の交代・ブラウザの
データ消去に対する備えがない。この課題を解消するため、データの書き出し（エクスポート）・
読み込み（インポート）機能を追加する。

自チーム版（Firestore）にも同機能を提供する。エクスポートの収集ロジックは
`CarpoolRepository`経由でストレージ非依存に書けるため共通化できる（6章参照）。

開発用「サンプルデータ投入」機能（`services/dev/seedSampleData.ts`）は本機能の
インポート処理と内容が重複するため、将来的に本機能へ統合できる見込みだが、
本ドキュメントの対象外とし、別タスクで検討する（8章）。

---

# 2. 対象範囲

- 公開版・自チーム版の両方
- 対象データ：集合場所・目的地・家庭・選手・コーチ・家族・イベント（配下の回答・
  配車結果を含む）全件
- 対象外：`staffUsers`（認証情報）。書き出し・読み込みいずれの対象にもしない

# 4. バックアップファイルの形式

- JSON、1ファイルにすべてのデータをまとめる
- ファイル名（案）：`carpoolbridge_backup_YYYYMMDD_HHmm.json`
  （実際のダウンロードファイル名はブラウザのダウンロード実装に依存し、指定通りに
  ならない場合があることを許容する）

## トップレベル構造

```typescript
interface BackupData {
  schemaVersion: 1;
  exportedAt: string; // ISO8601
  pickupLocations: PickupLocation[];
  destinations: Destination[];
  families: Family[];
  players: Player[];
  coaches: Coach[];
  familyMembers: FamilyMember[];
  events: Array<
    Event & {
      responses: ResponseWithFamilyId[];
      carpools: Carpool[];
    }
  >;
}
```

- `PickupLocation`・`Destination`・`Family`・`Player`・`Coach`・`FamilyMember`・
  `Event`・`ResponseWithFamilyId`・`Carpool`は既存の型（`src/types/master.ts`・
  `src/types/event.ts`）をそのまま使う
- `schemaVersion`は現在1固定。将来の形式変更に備えて持たせるが、当面マイグレーション
  処理は用意しない（不一致の場合は単純にエラーとし、部分復元は行わない。9章参照）
- 日付型はエクスポート時に`Date`から`toISOString()`した文字列とする。インポート時は
  文字列から`Date`に変換して書き込む（Firestore版は`FirestoreRepository`内部で
  `Timestamp`との変換を行う。`08_公開版アーキテクチャ設計.md`4章参照）

---

# 5. インポート時の処理方針（全置換）

1. ファイルをパースし、`schemaVersion`を検証する。パース失敗または非対応の
   `schemaVersion`の場合はエラーメッセージを表示して中断する（部分復元はしない）
2. 読み込み確認ダイアログ（`04_画面設計.md#10.5`）で「読み込む」が選択された場合の
   み以降を実行する
3. `repository.clearAllData()`で全データを物理削除する（6章）
4. ファイルの内容を、家庭→選手→コーチ→家族→集合場所→目的地→イベント→
   （イベントごとに）回答→配車結果、の順に書き込む（7章）
5. 完了後、ホーム画面へ遷移し、完了トーストを表示する（`04_画面設計.md#10.5`）

家庭・選手・コーチ・家族・イベント・回答・配車結果は互いにIDで参照し合うが、
Firestore・DexieいずれもDB側の外部キー制約は持たないため、書き込み順序自体に
技術的な制約はない。上記の順序は実装の見通しをよくするための推奨順であり、
途中でエラーが発生した場合に何がまだ書き込まれていないか把握しやすくする狙いがある。

# 6. CarpoolRepositoryインターフェースの拡張（`08_公開版アーキテクチャ設計.md`5章 改訂）

既存の`create*`系メソッドはIDを自動採番するため、バックアップの復元（元のIDのまま
書き込む必要がある）には使えない。以下を追加する。

```typescript
interface CarpoolRepository {
  // ...既存のメソッドに加えて

  // --- バックアップ復元専用（指定IDでの作成／上書き） ---
  restoreFamily(family: Family): Promise<void>;
  restorePlayer(player: Player): Promise<void>;
  restoreCoach(coach: Coach): Promise<void>;
  restoreFamilyMember(familyMember: FamilyMember): Promise<void>;
  restorePickupLocation(location: PickupLocation): Promise<void>;
  restoreDestination(destination: Destination): Promise<void>;
  restoreEvent(event: Event): Promise<void>;

  // --- バックアップ読み込み専用の全削除 ---
  clearAllData(): Promise<void>;
}
```

- `restore*`系は指定されたIDでドキュメントを作成・上書きする（upsert）。既存の
  `create*`系（新規登録画面からの呼び出し）とは別メソッドとし、既存の呼び出し元には
  一切影響を与えない
- `Response`・`Carpool`は既存の`createResponse(eventId, familyId, data)`・
  `saveCarpools(eventId, carpools)`が既にID指定の書き込みに対応しているため、
  新規メソッドは追加しない
- `clearAllData`は、families・players・coaches・familyMembers・pickupLocations・
  destinations・events（配下のresponses・carpoolsを含む）を全件物理削除する。
  バックアップ読み込み専用とし、他の画面・機能から呼び出さない
- エンティティ単位の`deleteAllX`を7つ追加するのではなく`clearAllData`1メソッドに
  集約する。バックアップの読み込みは常に「全部まとめて削除」であり、一部だけ削除する
  ユースケードが存在しないため（YAGNI）

## 実装上の注意（Firestore）

クライアントSDKに再帰削除・コレクション一括削除のAPIがないため、全件取得→バッチ削除
（500件区切り）で実装する。`services/dev/seedSampleData.ts`の
`deleteAllDocsInCollection`・`deleteAllEventsWithSubcollections`と同じ方式であり、
実装時にロジックが重複する。共通化（`FirestoreRepository`側に寄せ、
`seedSampleData.ts`から呼び出す形に変更する等）は8章で検討する。

`clearAllData`の途中でエラーが発生した場合、データが一部だけ削除された不完全な状態に
なり得る（Firestoreはコレクションをまたぐトランザクションを提供しないため）。この
状態からの自動復旧は行わない。エラー時は「データが不完全な状態の可能性があります。
バックアップファイルをもう一度読み込んでください」等のメッセージで運用でカバーする
（文言は実装時に確定する提案）。

## 実装上の注意（Dexie）

IndexedDBはDB内であればテーブルをまたいだトランザクションが可能なため、
`db.transaction('rw', 全テーブル, async () => { ... })`で`clearAllData`を実装し、
Firestore版のような不完全な状態が起きないようにする。

# 7. ビジネスロジック層（新設: `services/backup/backupService.ts`）

`08_公開版アーキテクチャ設計.md`7章の方針（複数のRepositoryプリミティブを組み合わせる
カスケード処理はRepositoryに含めず、service層の関数として置く）に従い、
以下をストレージ非依存のservice関数として実装する。

```typescript
async function exportAllData(): Promise<BackupData> { ... }
async function importAllData(data: BackupData): Promise<void> { ... }
```

- `exportAllData`：`getPickupLocations`・`getDestinations`・`getFamilies`・
  `getAllPlayers`・`getAllCoaches`・`getAllFamilyMembers`を呼び、
  `getUpcomingEvents(today)`と`getPastEventsPage`をカーソルが尽きるまでループして
  全イベントを収集する。各イベントについて`getResponses(eventId)`・
  `getCarpools(eventId)`を呼び、event本体に埋め込んでBackupData形式（4章）に
  組み立てる
- `importAllData`：`schemaVersion`を検証し（5章）、`repository.clearAllData()`の後、
  5章の順序で`restore*`・`createResponse`・`saveCarpools`を呼び出す

# 8. サンプルデータ投入機能との統合（提案・別タスク）

開発用「サンプルデータ投入」（`DevSampleResponseButton`の削除に続き、
`tasks/000_backlog.md`「X」参照）は、既存データを全削除したうえで固定IDのサンプル
データ（`services/dev/seedData.ts`）を投入する処理であり、本機能の`importAllData`
と処理内容が構造的に重複する。本機能の実装後、以下を別タスクとして検討する。

- `seedData.ts`の内容をBackupData形式に変換したフィクスチャファイルを用意する
- `DevSampleDataButton`を「（開発用）サンプルデータを読み込む」ボタンに置き換え、
  `importAllData`を呼び出す
- `seedSampleData.ts`の独自の全削除・投入ロジックを削除する
- `npm run seed`（`scripts/seed/seed.ts`）は`seedData.ts`を共用しているため、
  変換の影響有無を確認する

本ドキュメント・本機能の実装タスクの対象外とする。既存のサンプルデータ投入機能は
そのまま残す。
