# 1. 目的・位置づけ

本ドキュメントは、carpoolbridgeを不特定多数のチームへ公開する「公開版」のための
アーキテクチャ設計を定義する。

背景（2026-08-08付 公開化・収益化方針の検討より）:

- 個人情報を預からない設計とするため、公開版はサーバーへデータを一切送らず、
  端末内（IndexedDB/Dexie.js）にのみ保存する
- 自チーム版（Firestore）は温存し、公開版とは別ビルドとして並走させる
- 2リポジトリでのフォーク運用ではなく、1つのコードベース内で
  データ保存層のみを差し替える（リポジトリパターン）で実現する

`docs/01`〜`07`は自チーム版（Firestore版）の設計として引き続き正とする。
本ドキュメントは、公開版のために追加する**データ保存層の抽象化**のみを対象とし、
UI・配車アルゴリズム自体の仕様は変更しない。

# 2. 対象範囲・対象外

## 対象範囲

- `CarpoolRepository`インターフェースの定義
- 既存のFirestore直接呼び出し（`src/services/`配下10ファイル・91箇所＋
  `carpoolMember.ts`の`moveCarpoolMember`）をインターフェース経由に置き換える方針
  （8章参照）
- `storageMode`によるビルド分岐の仕組み

**コンポーネント・ページ・hooks側（`src/components`・`src/pages`・`src/hooks`配下、
現状12ファイルが`services/master/*`・`services/event/*`をimportしている）は変更しない。**
`services/`配下の各ファイルは公開関数名・シグネチャを変えずに残し、内部実装だけを
Repository呼び出しへ置き換える「薄いラッパー」として恒久的に維持する（5章参照）。
呼び出し元をRepositoryの直接呼び出しへ移行する案も検討したが、多くのコンポーネントが
複数エンティティのサービスを同時にimportしており（例:
`EventEditPage.tsx`は8モジュール）、対象ファイル数が10→22超に増え
`docs/50_タスク作成ルール.md`の粒度から外れるため採用しない。

- `DexieRepository`の実装そのもの（本ドキュメント確定後、別タスクで着手）
- Google Drive同期
- PWA化・TWA/Google Play公開・広告
- 認証（`staffUserService`）— 公開版では機構ごと削除する前提のため、
  Repositoryの対象にしない（3章参照）

# 3. 全体構成

```text
① UI（画面・コンポーネント）                          → 共通化・変更なし
② ビジネスロジック（配車アルゴリズム・削除カスケード等） → 共通化・変更なし
③ データ保存（Firestore / IndexedDB）                  → ここだけ CarpoolRepository 経由に差し替え
```

`storageMode`（`.env`等のビルド設定で指定）に応じて、アプリ起動時に注入する
Repository実装を切り替える。

- `storageMode: cloud` → `FirestoreRepository`（自チーム版）
- `storageMode: local` → `DexieRepository`（公開版）

認証（`staffUserService`、Firestoreの`staffUsers`コレクション参照）は、
公開版では機構ごと削除する前提のため、`CarpoolRepository`には含めない。
自チーム版でのみ従来通り独立して動作させる。

# 4. 型定義の変更点

`src/types/master.ts`・`src/types/event.ts`は現状、`createdAt`・`updatedAt`を
Firestore SDK固有の`Timestamp`型で定義している。IndexedDBにこの概念は存在しないため、
汎用の`Date`型に変更する。

```diff
- import { Timestamp } from 'firebase/firestore';
  ...
- createdAt: Timestamp;
- updatedAt: Timestamp;
+ createdAt: Date;
+ updatedAt: Date;
```

`FirestoreRepository`実装の内部で、Firestoreの`Timestamp`⇔`Date`の変換を吸収する
（書き込み時は`serverTimestamp()`、読み取り時は`.toDate()`）。

`PickupLocation`・`Destination`は元々`createdAt`/`updatedAt`を持たないため変更不要。

併せて、`src/components/eventEdit/FamilyResponseCard.tsx`など`Timestamp`型を
直接importしているコンポーネントは、`Date`型を参照するよう修正する。これにより
コンポーネント層からFirestore SDKへの直接依存がなくなる。

# 5. CarpoolRepositoryインターフェース

既存の`src/services/`配下の関数名・シグネチャをそのまま踏襲する。ここでいう「呼び出し側」は
各serviceファイル内部のFirestore SDK呼び出し（91箇所）を指す。コンポーネント・ページ・
hooks側（2章参照）は`services/`の関数を今まで通り呼び続けるため、一切変更しない。
型は4章の変更を反映したものを使う。

```typescript

  // --- Player ---

    destinationId: string,
    data: Partial<Pick<Destination, 'name' | 'latitude' | 'longitude'>>

  createEvent(data: Omit<Event, 'id' | 'createdAt' | 'updatedAt'>): Promise<string>;
```

タスクをエンティティ単位（8章）に分割しやすくするため、実装は次の構成にする。

# 6. saveCarpoolsの新設について

`moveCarpoolMember`（配車結果のドラッグ&ドロップ、`src/services/carpool/carpoolMember.ts`）は
移動元・移動先2件のCarpoolドキュメントを1つのFirestoreバッチで同時更新している。
片方だけ成功して乗客がどの車にも属さない状態になる事故を防ぐためであり、
既存の`updateCarpool`（1件・部分更新）だけではこの安全性を表現できない。

そのため`saveCarpools(eventId, carpools: Carpool[])`を新設する。

**セマンティクスはupsertのみとする。** 渡された配列の各要素をそれぞれcreate/updateするだけで、
そのイベントの他のCarpoolドキュメントには一切手を触れない（削除しない）。「渡した配列でその
イベントの配車結果全体を置き換える」という解釈はしない。`moveCarpoolMember`は変更のあった
1〜2件のみを渡す運用を前提とするため、全置換の意味だと誤って実装すると、ドラッグ&ドロップの
たびに他の車の配車データが消えてしまう。

- `FirestoreRepository`: `writeBatch`で実装（既存の`moveCarpoolMember`と同じ安全性を維持）
- `DexieRepository`: Dexieのトランザクション（`db.transaction('rw', ...)`）で実装

`moveCarpoolMember`自体は`carpoolMember.ts`に残すが、Firestore（`writeBatch`）への
直接依存をやめ、`repository.saveCarpools(...)`を呼ぶ形に書き換える。

# 7. Repositoryに含めない処理（ビジネスロジック層に残すもの）

以下は複数のRepositoryプリミティブを組み合わせた「カスケード処理」であり、
Firestore固有API（`writeBatch`等）を使わない形にすればストレージ非依存になる。
Repositoryのメソッドとしては追加せず、各serviceファイルに関数として残す。

| 関数 | 現状の実装 | 変更後の実装 |
|---|---|---|
| `familyService.deleteFamily` | 選手・コーチ・家族を道連れ削除→家庭削除 | `repository.deletePlayersByFamilyId`等を順に呼ぶだけに変更（ロジック自体は不変） |
| `eventService.deleteEvent` | 回答・配車結果を全削除→イベント削除 | 同上 |
| `carpoolService.deleteCarpoolsByDirection` | `getCarpools`→ループで`deleteCarpool` | 同上（既にstorage非依存に近い） |

この整理により、`FirestoreRepository`・`DexieRepository`のどちらも
「カスケード削除ロジックの二重実装」を持たずに済む（3章の三層構成の通り、
②ビジネスロジックは完全共通化する）。
