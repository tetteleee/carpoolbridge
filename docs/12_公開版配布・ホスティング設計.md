# 2. 経緯（別プロジェクトを選んだ理由）

当初、既存の自チーム版プロジェクト（`carpoolbridge`）にHosting siteを追加する
マルチサイト構成（同一プロジェクト内で自チーム版・公開版を共存させる案）を検討したが、
以下の理由により不採用とした。

**問題点**: Firebase Hostingの無料枠（Sparkプラン）は「サイト単位」ではなく
**プロジェクト単位**で合算される。公開版の利用者が増えて日次転送量の無料枠を
使い切ると、同一プロジェクト内の自チーム版まで巻き添えで配信不可になる。
Sparkプランは課金アカウントを持てないため、枠超過時は追加料金が発生するのではなく
その日の配信自体が止まる。試合当日に配車を確認できない事態が、自チーム版とは
無関係な公開版の利用状況によって起こり得るのは、`CLAUDE.md`が最優先とする
「現場で使えること」「乗せ忘れを防ぐこと」と相容れない。

**変更案**: 公開版を別Firebaseプロジェクト（`carpoolbridge-go`）に分離する。

**メリット**: 自チーム版の可用性が公開版の利用状況に一切左右されなくなる。
無料枠もプロジェクトごとに独立するため、公開版が伸びても自チーム版に影響しない。

**デメリット**: Firebase CLIのproject alias設定、GitHub Actionsのsecrets追加など、
初期セットアップの手間が同一プロジェクト案よりわずかに増える。運用開始後の
追加コストはほぼない。

# 3. 独自ドメインについて（当面見送り）

独自ドメインの取得には費用（`.com`で年1,000〜1,500円程度）がかかる。
「可能な限り無料で始めたい」という方針のため、当面はFirebase Hostingが無料で
提供するサブドメイン（`carpoolbridge-go.web.app`）をそのまま使う。

独自ドメインは、Firebase Hosting自体に無料で追加できる機能である
（ドメイン購入費以外の追加コストは発生しない）。そのため、収益化の見通しが
立った際に検討すればよく、**その時点でもホスティング事業者を変える必要はない**
（＝Firebaseにとどまったまま独自ドメインだけ追加できる）。

参考: 他社ホスティング（GitHub Pages/Vercel/Netlify等）への将来的な移行自体は
可能だが、PWAはオリジン（ドメイン）に紐付くため、ホスティング事業者を変えて
URLが変わると、既にホーム画面に追加（インストール）済みのユーザーは
再インストールが必要になる。この影響を避けるため、他社ホスティングへの移行は
「Firebaseでは満たせない具体的な理由が生じた場合」にのみ検討する方針とし、
現時点では計画しない。

# 4. デプロイ方式

自チーム版と同様、`main`マージ時にGitHub Actionsで自動デプロイする。
既存の`.github/workflows/firebase-deploy.yml`（E2E Tests成功後に発火する
`workflow_run`トリガー）に、公開版のビルド・デプロイのステップを追加する形で拡張する。
新規workflowファイルには分けない（自チーム版と同じトリガー条件・実行タイミングを
共有するため、既存ワークフロー内にステップを追加する方が単純）。

自チーム版のデプロイ（Firestore Rules・Hosting）とは独立したステップとして追加し、
一方が失敗してももう一方のデプロイ結果に影響しないようにする。

## 4.1 認証情報

`carpoolbridge-go`プロジェクトのサービスアカウントキーを発行し、GitHub Secretsに
`FIREBASE_SERVICE_ACCOUNT_PUBLIC`として登録する（既存の自チーム版用
`FIREBASE_SERVICE_ACCOUNT`とは別のsecret）。この作業は人間が行う
（Firebaseコンソール上の操作のため）。

## 4.2 firebase.json・.firebasercの扱い

公開版はFirestore・Authenticationを使わない（`docs/08`#2）ため、
`carpoolbridge-go`プロジェクトではHostingのみを有効化する。

`firebase.json`の`hosting`設定（`public: "dist"`、SPA向けrewrite）は自チーム版・
公開版で共通のまま流用できる。`npm run build`と`npm run build:public`は
どちらも同じ`dist/`ディレクトリに出力するため（`vite.config.ts`に`outDir`の
上書きなし）、CI側で「該当のmodeでビルド→そのプロジェクトへデプロイ」を
順番に実行すれば、ビルド成果物の混在は起きない。

`.firebaserc`に公開版プロジェクトのaliasを追加する。

```json
{
  "projects": {
    "default": "carpoolbridge",
    "public": "carpoolbridge-go"
  }
}
```

## 4.3 ワークフローの追加ステップ（イメージ）

既存の「Build」「Deploy Firebase Hosting」ステップ（自チーム版向け）の後に、
公開版向けのビルド・デプロイステップを追加する。

```yaml
      - name: Build (public)
        run: npm run build:public

      - name: Deploy Firebase Hosting (public)
        uses: FirebaseExtended/action-hosting-deploy@v0
        with:
          firebaseServiceAccount: ${{ secrets.FIREBASE_SERVICE_ACCOUNT_PUBLIC }}
          projectId: carpoolbridge-go
          channelId: live
```

公開版はFirestore Rulesのデプロイステップが不要（Firestoreを使わないため）。
自チーム版向けの`Deploy Firestore Rules`ステップとは無関係に追加する。

`docs/50_タスク作成ルール.md`の粒度に従い、以下の2タスクに分割する。

| タスク | 内容 | 変更対象ファイル |
|---|---|---|

人間の作業であり、タスク化の対象外とする（Firebaseコンソール・GitHub設定画面上の
操作のため、リポジトリへの変更を伴わない）。
