# 配車アルゴリズム

本ドキュメントは、学童野球配車支援システムにおける自動配車アルゴリズムの論理設計を定義する。
「人間の配車担当者が行う調整業務の80〜90%を自動化し、最終確認・手動修正を前提とする」というMVP方針に基づき、巡回順（ルーティング）算出などスコープ外の要素は排除しつつ、「未配車人数」「同一集合場所の集約度」「総移動距離」の3点については**分枝限定法（Branch and Bound）による厳密最適化**を行う設計を採用する。

---

## 1. 設計方針とシンプル化の論理的根拠

本アルゴリズムは、実装コストを最小化しつつ実用的な配車案を出力するため、以下の「引き算」の設計を行っている。

* **ルーティング機能の非搭載**:
  * 目的地までの最適巡回順の自動算出は行わない。実際の運用では、ドライバーが各自の使い慣れたナビアプリ等で最適ルートを選択するため、システム側では「同じ車に乗るメンバー（車ごとの集合場所リスト）」の確定に特化する。これにより、巡回順の反転補正ロジックやそれらに伴う保守コストを完全に排除する。
* **ドライバーの集合場所を起点とした距離評価**:
  * 経路全体との距離ではなく、「ドライバーの集合場所」と「グループの集合場所」の2点間距離のみを静的に評価する。これにより、割り当て状況によって評価関数が複雑化するのを防ぎ、テスト容易性（Testability）を最大化する。
* **厳格な事前バリデーション（Early Exit）**:
  * 緯度経度が未登録の地点や、優先割り当て時の定員超過などのデータ不整合がある場合、不完全なデータで強引に計算を進めるペナルティ処理（Soft Fail）は行わない。処理の先頭でエラー（Hard Fail）として検知・中断し、ユーザーへ修正を促すことで、不正データの伝播を防ぐ。
* **目的関数の段階数の最小化**:
  * 割当案の質を評価する目的関数は、優先順位付きの3段階（未配車人数 → 同一集合場所の超過訪問数 → 総移動距離）に絞る。使用車両台数、車両ごとの空席数の偏り、経由地数の偏り、季節を通じた運転負担の公平性といった副次的な指標は目的関数に含めない。これらは実運用上、自動配車後のドラッグ＆ドロップによる手動微調整で十分にカバーできると判断し、目的関数を複雑化させない（YAGNI）。

## 2. 前処理フェーズ（制約の事前解決とデータ構造化）

探索範囲を最小化し、業務上の絶対制約を事前に保証するため、メインループロジックの前にデータを以下の構造に変換する。
依存関係を正しく解決するため、バリデーションと構造化は以下の順序で厳密に実行する。

### 2.1 データの初期化と基本バリデーション
1. **緯度経度チェック（Early Exit）**:
   * 配車対象の全集合場所およびドライバーの集合場所において、緯度・経度が設定されているか検証する。未設定の地点が1つでもある場合は**自動配車処理をエラーで中断**し、エラー原因となった地点名を管理画面に通知する。
2. **車両データの初期化**:
   * 対象方向（行き/帰り）の車出しフラグが `true` である車両 $V$ を抽出する。
   * **有効定員** $remainingCapacity_V$ **の算出**: 
     $$remainingCapacity_V = V.\text{capacity}$$
     （※有効定員は車両の定員そのものとする。家庭に参加するコーチが紐づく場合、そのコーチ自身が
     乗車メンバーとして乗車メンバー数・定員消費数に含まれる）

### 2.2 家族グループ（Family Group）の形成
「兄弟は同じ車」「乗客コーチは所属家庭の子供と同じ集合場所から乗車」という絶対制約をコードの構造で解決するため、乗客を**家庭（familyId）単位で1つの「グループ G」**に統合する。

* **グループ $G$ のプロパティ（データ構造の統一）**:
  * `familyId`: 所属家庭ID
  * `size`: 必要席数（グループを構成する乗車メンバー人数。家庭に参加コーチがいる場合はそのコーチ自身の1名を含む）
  * `pickupLocationId`: 集合場所ID（永続化・同値比較用）
  * `pickupLocation`: 座標オブジェクト（アルゴリズムの距離計算用：緯度・経度）

### 2.3 優先割り当てグループの定員検証と割当
1. **定員超過チェック（Early Exit）**:
   * 車両 $V$ に強制的に割り当てられるドライバー家庭のグループ $G_{\text{driver}}$ （ドライバー本人を除いた、同乗必須の家族グループ）の必要席数 $G_{\text{driver}}.\text{size}$ が、車両の有効定員 $remainingCapacity_V$ を超過しているか検証する。
   * もし超過している車両が存在する場合、**自動配車処理を不整合データとして即時中断**し、対象ドライバー名をエラーとして通知する。
2. **ドライバー家族の優先割り当て**:
   * 各車両 $V$ に対応するグループ $G_{\text{driver}}$ を割り当て、車両の空き定員を更新する。
     $$remainingCapacity_V \leftarrow remainingCapacity_V - G_{\text{driver}}.\text{size}$$
   * 優先割り当て済みのグループは、以降の自動配車対象リスト（未配車グループ配列）から除外する。

## 3. 目的関数（配置適合度評価）

未割り当てのグループ $G$ の集合を車両 $V$ の集合へ割り当てる組み合わせ（以下「割当案」）の適合度を評価するため、以下の3段階の目的関数を**優先順位付き（辞書式順序／Lexicographic Order）**で定義する。

$$\text{Objective}(\text{割当案}) = (\ \text{UnassignedCount},\ \text{ExcessVisitCount},\ \text{TotalDistance}\ )$$

比較は辞書式順序で行う。すなわち $\text{UnassignedCount}$ が小さい割当案を常に優先し、そこが同値の場合のみ $\text{ExcessVisitCount}$ を比較し、そこも同値の場合のみ $\text{TotalDistance}$ を比較する。いずれの値も小さいほど良い割当案である。

> **注意（評価値の性質と副作用の排除）**
> * 目的関数を計算する処理は**副作用を一切持たない純粋関数（Pure Function）**として設計する。引数として渡されたグループや車両オブジェクトの状態を書き換える（破壊的変更を加える）ことは一切せず、与えられた情報から評価値を算出・返却する責任のみを負う。

### 第1優先：未配車人数の最小化（$\text{UnassignedCount}$）
* **定義**: どの車両にも割り当てられなかったグループの構成員数の合計。
* **意図**: 「乗せ忘れを防ぐ」という本システムの最優先事項（プロジェクト概要参照）を、目的関数の最上位に据えて保証する。

### 第2優先：同一集合場所の超過訪問数の最小化（$\text{ExcessVisitCount}$）
* **定義**: 割当案において、ある集合場所を訪問する車両の台数を $\text{visitCount}(\text{location})$ としたとき、
  $$\text{ExcessVisitCount} = \sum_{\text{location}} \max(0,\ \text{visitCount}(\text{location}) - 1)$$
  * 1つの集合場所が2台の車両に分かれれば+1、3台に分かれれば+2……と、分散の深刻さに応じて加算する（単純な「分割された場所の件数」ではなく、分割の度合いそのものを評価する）。
* **意図**: 同じ集合場所に集まるメンバーをできる限り同一の車両にまとめる。より軽微な分散（2台への分割）を、より深刻な分散（3台以上への分割）より優先的に許容する。

### 第3優先：総移動距離の最小化（$\text{TotalDistance}$）
* **定義**: 割当案に含まれる全てのグループ $G$ について、割当先車両 $V$ のドライバー集合場所（`driverPickupLocation`）とグループの集合場所（`pickupLocation`）の間のハバーシン公式による直線距離（km）を合計した値。
  $$\text{TotalDistance} = \sum_{(G,\ V)\ \in\ \text{割当案}} \text{Distance}(G, V)$$
* **意図**: 地域的に近いメンバー同士を同じ車両にまとめる。第1・第2優先が同値となる複数の割当案が存在する場合の、最終的な効率化指標として機能する。

### 決定論的動作のための最終タイブレーク
第1〜第3優先の目的関数値が完全に同値となる割当案が複数存在する場合でも、常に同一の割当案を一意に選ぶため、以下の探索順序を固定し、**探索木を辿って最初に見つかった最良解を採用し、後から見つかった同値の解では上書きしない**（実装方針は4節参照）。
* グループの探索順序：構成員数（`size`）の降順、同数の場合はfamilyIdの昇順
* 車両の探索順序：**その時点でグループの集合場所を既に訪問済みの車両を優先し、その中でdriverFamilyIdの昇順**（未訪問の車両は、訪問済みの車両をすべて試した後に、同じくdriverFamilyIdの昇順で試す）。「訪問済みかどうか」は探索中の部分的な割当状態（`pickupLocationIds`）に応じて動的に変わるが、グループ探索順序が決定論的である以上、この判定自体も決定論的である。
  * この順序により、同一集合場所への集約を優先的に発見しやすくなり、時間予算内での枝刈り効率・収束速度が大きく向上する（5節参照）。

## 4. 割り当てフェーズ（分枝限定法による厳密探索）

3節で定義した目的関数を最小化する割当案を、**分枝限定法（Branch and Bound）による網羅的探索**で求める。局所最適に陥る貪欲法とは異なり、探索空間を漏れなく辿ることで理論上の最良解（厳密解）を保証する。

### 4.1 決定論的動作（再現性）の保証
実行環境やデータベースのレコード取得順に依存せず、常に100%同一の入力に対して同一の配車結果を出力するため、以下を厳密に定義する。

1. **配列順序の保護（Shallow Copyの適用）**:
   * メインロジック内でのソート処理が、引数として渡された元配列の並び順を破壊しないよう、車両配列およびグループ配列を複製（シャローコピー）した上でソート処理を行う。
   * *※探索中の割当は`Vehicle`オブジェクトのプロパティ（members・remainingCapacity・pickupLocationIds等）へ直接ミューテーションを加えるが、バックトラック時に必ず逆操作で元の状態へ戻す（後述4.2）。探索完了後、最終的に確定した最良解のみを一度だけ反映する。*
2. **探索順序**: 3節「決定論的動作のための最終タイブレーク」で定義したグループ探索順序（構成員数降順→familyId昇順）・車両探索順序（訪問済み優先→driverFamilyId昇順）を、分枝限定法の分岐順序としてそのまま用いる。
3. **同点時の優先順位**:
   * 探索によって複数の割当案が同一の目的関数値（3節のObjective）となった場合は、**上記の探索順序で最初に見つかった割当案を優先（先勝ち）**とする。疑似コード上では、最良解の更新条件を厳密な不等号で評価することで、同点時に後続の割当案による上書きを防ぐ。

### 4.2 配車処理フロー（疑似コード）

```typescript
interface Location {
  latitude: number;
  longitude: number;
}

interface Passenger {
  id: string;
  name: string;
}

interface Group {
  familyId: string;
  size: number;
  pickupLocationId: string; // 永続化・比較用ID
  pickupLocation: Location; // アルゴリズム用座標オブジェクト
  members: Passenger[];
}

interface Vehicle {
  id: string;
  driverFamilyId: string;
  remainingCapacity: number; // 算出方法は2.1節参照（車両の定員そのもの）
  driverPickupLocationId: string; // 永続化・比較用ID
  driverPickupLocation: Location; // アルゴリズム用座標オブジェクト
  pickupLocationIds: Set<string>; // 経由予定の集合場所IDセット（O(1)検索用）
  members: Passenger[];
}

// 3節で定義した目的関数の値（辞書式順序で比較する3つ組）
interface ObjectiveValue {
  unassignedCount: number;
  excessVisitCount: number;
  totalDistance: number;
}

// aがbより優れていれば負、劣っていれば正、同値なら0を返す（辞書式比較）
function compareObjective(a: ObjectiveValue, b: ObjectiveValue): number {
  if (a.unassignedCount !== b.unassignedCount) return a.unassignedCount - b.unassignedCount;
  if (a.excessVisitCount !== b.excessVisitCount) return a.excessVisitCount - b.excessVisitCount;
  return a.totalDistance - b.totalDistance;
}

function runAutoAssignment(
  vehicles: Vehicle[],
  unassignedGroups: Group[]
): { assignedVehicles: Vehicle[]; unassignedList: Group[] } {

  // 1. 車両・グループ配列のコピーと決定論的ソート（3節の探索順序）
  const sortedVehicles: Vehicle[] = [...vehicles].sort((a, b) =>
    a.driverFamilyId.localeCompare(b.driverFamilyId)
  );
  const sortedGroups: Group[] = [...unassignedGroups].sort((a, b) => {
    if (b.size !== a.size) return b.size - a.size;
    return a.familyId.localeCompare(b.familyId);
  });

  // 集合場所ID → 現在訪問中の車両数（超過訪問数の算出用の作業状態）
  const visitCountByLocation = new Map<string, number>();

  let best: { objective: ObjectiveValue; assignments: Map<Group, Vehicle | null> } | null = null;

  function currentObjective(unassignedCount: number, distanceSum: number): ObjectiveValue {
    let excessVisitCount = 0;
    for (const count of visitCountByLocation.values()) {
      excessVisitCount += Math.max(0, count - 1);
    }
    return { unassignedCount, excessVisitCount, totalDistance: distanceSum };
  }

  // グループを1件ずつ「どの車両に割り当てるか／未配車のままにするか」再帰的に決定する
  function search(
    index: number,
    unassignedCount: number,
    distanceSum: number,
    assignments: Map<Group, Vehicle | null>
  ): void {
    // 枝刈り: 暫定値は最終的な目的関数値の下界（unassignedCount・excessVisitCount・
    // distanceSumはいずれも以降の決定で単調非減少）なので、既に最良解より劣っていれば打ち切ってよい
    if (best !== null && compareObjective(currentObjective(unassignedCount, distanceSum), best.objective) > 0) {
      return;
    }

    // 葉に到達: 全グループの決定が完了
    if (index === sortedGroups.length) {
      const objective = currentObjective(unassignedCount, distanceSum);
      // 厳密な不等号により、同点時は先に見つかった解（探索順序が優先する解）を保持する
      if (best === null || compareObjective(objective, best.objective) < 0) {
        best = { objective, assignments: new Map(assignments) };
      }
      return;
    }

    const group = sortedGroups[index];

    // 選択肢a: 乗車可能な車両へ割り当てる（車両探索順序で試す）
    for (const vehicle of sortedVehicles) {
      if (vehicle.remainingCapacity >= group.size) {
        const isNewStop = !vehicle.pickupLocationIds.has(group.pickupLocationId);
        const distance = getHaversineDistance(vehicle.driverPickupLocation, group.pickupLocation);

        // 仮に割り当てる
        vehicle.remainingCapacity -= group.size;
        vehicle.pickupLocationIds.add(group.pickupLocationId);
        visitCountByLocation.set(
          group.pickupLocationId,
          (visitCountByLocation.get(group.pickupLocationId) ?? 0) + 1
        );
        assignments.set(group, vehicle);

        search(index + 1, unassignedCount, distanceSum + distance, assignments);

        // バックトラック: 仮の割当を取り消して元の状態へ戻す
        assignments.delete(group);
        const remaining = (visitCountByLocation.get(group.pickupLocationId) ?? 1) - 1;
        if (remaining === 0) {
          visitCountByLocation.delete(group.pickupLocationId);
        } else {
          visitCountByLocation.set(group.pickupLocationId, remaining);
        }
        if (isNewStop) vehicle.pickupLocationIds.delete(group.pickupLocationId);
        vehicle.remainingCapacity += group.size;
      }
    }

    // 選択肢b: 未配車のままにする
    assignments.set(group, null);
    search(index + 1, unassignedCount + group.size, distanceSum, assignments);
    assignments.delete(group);
  }

  search(0, 0, 0, new Map());

  // 最良解をVehicleへ確定反映する（探索中の仮割当はすべてバックトラックで戻っているため、ここで一度だけ反映する）
  const unassignedList: Group[] = [];
  for (const [group, vehicle] of best!.assignments) {
    if (vehicle) {
      vehicle.members.push(...group.members);
      vehicle.remainingCapacity -= group.size;
      vehicle.pickupLocationIds.add(group.pickupLocationId);
    } else {
      unassignedList.push(group);
    }
  }

  return { assignedVehicles: sortedVehicles, unassignedList };
}
```

## 5. 計算量（Complexity）

分枝限定法は理論上の最悪ケースでは組合せ的爆発を起こしうる。グループ数を $N_G$ （家族単位に統合されているため $N_G \le N$）、車両数を $M$ としたとき、各グループに「$M$台のいずれかへ割り当てる」または「未配車のままにする」の $M+1$通りの選択肢があるため、理論上の最悪計算量は $O((M+1)^{N_G})$ となる。

ただし、実用スケール（乗客数 $N \le 40$、車両数 $M \le 10$）においては、以下の理由により枝刈りが強く効き、現実的な時間内に探索が完了すると想定する。

* **定員制約による分岐の削減**: 各グループについて、残定員が足りない車両は分岐の対象から除外されるため、実際の分岐数は $M+1$ より小さくなることが多い。
* **目的関数による枝刈り**: 4.2節の枝刈り条件（暫定の目的関数値が既知の最良解を上回れば探索を打ち切る）により、明らかに最良解を更新し得ない分岐は早期に打ち切られる。特に第1優先（未配車人数）による枝刈りの効果が大きい。
* **家族単位のグループ化**: 前処理フェーズ（2.2節）で乗客を家庭単位に統合しているため、探索対象となるグループ数 $N_G$ は乗客数 $N$ より少ない。
* **訪問済み優先の車両探索順序**: 3節で定義した車両探索順序（同一集合場所を訪問済みの車両を優先）により、同一集合場所への集約を早い段階で発見しやすくなる。強い暫定解を早期に確立できると、以降の枝刈り（上記の目的関数による枝刈り）がより多くの分岐を早期に切り落とせるため、収束速度に大きく寄与する。

なお、本アルゴリズムは決定論的に動作するが、計算量そのものは理論上の最悪ケースを保証するものではない。実際、当初の実装（車両探索順序が単純なdriverFamilyId昇順のみ）では、家族グループ20〜30件・車両8〜10台程度の実用規模を想定した検証データでも、枝刈りだけでは数秒〜数十秒以上探索が終わらないケースが確認されており、モバイル端末（iPhone Safari等）ではタブがクラッシュする実害が発生した。上記の訪問済み優先の車両探索順序を導入した後は、同規模の検証データ（複数パターン）で数十ミリ秒程度に収束することを確認しているが、これは特定のデータ分布における実測結果であり、理論上の最悪ケースの解消を意味するものではない。

### 5.1 時間予算による打ち切りとフォールバック
上記の理由により、探索には**時間予算（`SEARCH_TIME_BUDGET_MS` = 1000ミリ秒）**を設ける。予算を超過した時点で新たな分岐への展開を打ち切り、**その時点で見つかっている最良解（暫定解）**をそのまま採用する。

「配車作成」操作は行き・帰り2方向分、本探索を2回連続で呼び出すため、1回あたりの予算は、モバイル端末のメインスレッドを合計で長時間ブロックしないよう短めに設定している（2回合計で最大約2秒）。

* 深さ優先探索の性質上、探索開始から最初の葉（全グループの決定が完了した状態）に到達するまでの経路は、各グループについて「探索順序上最初に見つかった乗車可能な車両」を選び続けるだけの浅い経路であり、実用データ規模では瞬時に到達する。したがって時間予算に達した時点で「実行可能な割当案が1つも見つかっていない」事態は実質的に発生しない。
* この対策により、**目的関数（3節）に対する厳密最適性の保証は「時間予算内に探索が完了した場合に限る」**ものとなる。時間予算超過時に採用される暫定解は、実行可能（定員・優先割当等の制約を満たす）ではあるが、理論上の最良解であることは保証されない。この点は7節「アルゴリズムの限界」にも明記する。

## 7. アルゴリズムの限界と運用上の位置づけ

本アルゴリズムは、人間の配車担当者が行う調整の大部分を自動化し、初期配車案を高速に提示することを目的として設計されている。

* **決定論的アルゴリズムとしての再現性**:
  本アルゴリズムは決定論的（Deterministic）に動作するよう厳密に設計されており、**同一の入力データセットに対しては常に100%同一の結果を出力する（高い再現性の保証）**（ref: 3節「決定論的動作のための最終タイブレーク」）。
* **3段階の目的関数における厳密最適性（時間予算内に限る）**:
  本アルゴリズムは、3節で定義した目的関数（未配車人数 → 同一集合場所の超過訪問数 → 総移動距離、の優先順位）については、分枝限定法による網羅的探索によって**理論上の最良解（厳密解）を保証する**。局所最適に陥る貪欲法とは異なり、この3指標に関して「これより良い割当は存在しない」ことが保証される。
  ただし5.1節の時間予算による打ち切りが発生した場合は、厳密最適性は保証されず、その時点までに見つかった実行可能な暫定解が採用される。この場合でも、未配車人数を無制限に増やすような明らかに悪い解が採用されることは、深さ優先探索の探索順序（3節参照）上、実用データでは起こりにくい。
* **目的関数に含まれない要素は最適化の対象外**:
  使用車両台数、車両ごとの空席数の偏り、経由地数の偏り（特定のドライバーへの負担集中）、季節を通じた運転負担の公平性などは目的関数に含まれていないため、最適化の対象外である。これらは実運用上、自動配車後にユーザー自身がUI上でドラッグ＆ドロップにより手動微調整を行うことを前提とする。将来的にこれらの要素を目的関数に含める必要が生じた場合は、本ドキュメントの改訂と合わせて検討する。
