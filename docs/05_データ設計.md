# 3. Family（家庭）

1家庭につき1レコード

| 項目 | 型 | 必須 | 説明 |
| --- | --- | --- | --- |
| id | String | ○ | ID |
| familyName | String | ○ | 〇〇家 |
| vehicleCapacity | Number | ○ | 車の総定員（運転者本人を含む。車を持たない場合は0） |
| pickupLocationId | String | ○ | 家庭の集合場所（家庭に属する選手・コーチ・家族は全員この集合場所から乗車する） |
| isActive | Boolean | ○ | 在籍中（falseで卒団・非表示扱い） |
| createdAt | Timestamp | ○ | |
| updatedAt | Timestamp | ○ | |

- 家庭の`isActive`をfalseにしても、配下の選手・コーチ・家族の`isActive`は書き換えない（各自の値をそのまま保持する）
- 新規イベントの回答・配車対象からの除外判定は「家庭`isActive` AND 本人`isActive`」のAND条件で行う。家庭が無効な間は本人の値に関わらず除外され、家庭を再度有効に戻すと本人の`isActive`の値どおりに復帰する
- 登録情報画面では、家庭が無効な間、配下の選手・コーチ・家族の「在籍中」トグルは操作不可（disabled）にしてグレーアウト表示する（実データは変更しないため、家庭を有効に戻すと各自の値どおりの表示・操作可能状態に戻る。04_画面設計.md#10 登録情報）

### 運転者・家庭の表示名

保護者名の個別入力は行わない。車カード・LINE共有・乗車メンバー表示に
出る運転者名は、familyNameから「家」を除いた文字列（例：山田家→山田）を
そのまま使用する。コーチ・家族（FamilyMember）が運転する場合も同様に、
運転者個人名（本人の名前）は使用せず、家庭表示名をそのまま使用する
（運転者個人を特定するデータは持たないため）。

※本設計では「保護者」という専用のデータ種別は持たない。運転者・乗車者の種別は
「選手（Player）」「コーチ（Coach）」「家族（FamilyMember）」の3種のみとする。
家族は保護者・祖父母・兄弟などを区別せず、同一の種別として扱う。

# 4. Player（選手）

| 項目 | 型 | 必須 | 説明 |
| --- | --- | --- | --- |
| id | String | ○ | |
| familyId | String | ○ | |
| name | String | ○ | |
| schoolEntryYear | Number | ○ | 小学校の入学年度（例：2026）。学年はこの値から自動計算する |
| isActive | Boolean | ○ | 在籍中（falseで卒団・非表示扱い） |
| createdAt | Timestamp | ○ | |
| updatedAt | Timestamp | ○ | |

- 選手の`isActive`は家庭の`isActive`から独立して保持する（家庭を無効化しても選手自身の`isActive`は書き換えない。除外判定はAND条件で行う。前章「Family」参照）
- 選手の集合場所は個別に設定できない。所属家庭の`Family.pickupLocationId`を常に使用する（同一家庭内で集合場所が分かれるケースは許容しない）

# 4a. Coach（コーチ）

選手の保護者がコーチを兼ねる場合に登録する。1人につき1レコード。1家庭に複数人登録できる（人数の上限なし）。

| 項目 | 型 | 必須 | 説明 |
| --- | --- | --- | --- |
| id | String | ○ | |
| familyId | String | ○ | |
| name | String | ○ | |
| isActive | Boolean | ○ | 在籍中（falseで非表示扱い） |
| createdAt | Timestamp | ○ | |
| updatedAt | Timestamp | ○ | |

- コーチの`isActive`は家庭の`isActive`から独立して保持する（選手・家族と同様。前章「Family」参照）
- コーチの集合場所は個別に設定できない。所属家庭の`Family.pickupLocationId`を常に使用する（選手・家族と同じ扱い）
- 学年に相当する項目は持たない（対象が選手に限らないため。FamilyMemberと同様）
- 表示順は登録順とする。学年のような属性による自動ソートは行わない（FamilyMemberと同じ理由）

### 家族との違い

`FamilyMember`（家族）とは別のデータとして扱う（統合しない）。次章「FamilyMember」の「コーチとの違い」を参照。

# 5. FamilyMember（家族）

選手・コーチ以外で配車の対象になり得る人（兄弟・祖父母など）を表す。1人につき1レコード。1家庭に複数人登録できる（人数の上限なし）。

| 項目 | 型 | 必須 | 説明 |
| --- | --- | --- | --- |
| id | String | ○ | |
| familyId | String | ○ | |
| name | String | ○ | |
| isActive | Boolean | ○ | 在籍中（falseで非表示扱い） |
| createdAt | Timestamp | ○ | |
| updatedAt | Timestamp | ○ | |

- 家族の`isActive`は家庭の`isActive`から独立して保持する（選手・コーチと同様。前章「Family」参照）
- 家族の集合場所は個別に設定できない。所属家庭の`Family.pickupLocationId`を常に使用する（選手と同じ扱い）
- 学年に相当する項目は持たない（対象が選手に限らないため）
- 表示順は登録順とする。学年のような属性による自動ソートは行わない（本章冒頭のPlayerと異なり、並び替えの基準となる属性を持たないため）

### コーチとの違い

`Coach`（コーチ）とは別のデータとして扱う（統合しない）。コーチは「コーチ」という役職を表すデータであるのに対し、家族は選手・コーチ以外の同乗者（兄弟・祖父母等）を表すデータである。将来、選手・コーチのみの車と家族のみの車を区別する運用（応援号など）を見据え、意図的に統合しない（09_今後のアイデア.md参照）。

# 6. PickupLocation（集合場所）

| 項目 | 型 | 必須 | 説明 |
| --- | --- | --- | --- |
| id | String | ○ | |
| name | String | ○ | |
| latitude | Number \| null | ○ | 緯度。未入力の場合はnull（緯度経度未設定） |
| longitude | Number \| null | ○ | 経度。未入力の場合はnull（緯度経度未設定） |

### 緯度経度の未設定について

登録時点では地図上の座標が分からない場合があるため、latitude・longitudeは手入力必須項目とはせず、未入力の場合はnullを保存する。
自動配車処理は開始前に全集合場所の緯度経度が設定済みであることを検証し、nullが1件でも存在する場合はエラーで中断する
（[07_配車アルゴリズム.md#2.1](07_配車アルゴリズム.md)）。

# 8. Event（イベント）

| 項目 | 型 | 必須 | 説明 |
| --- | --- | --- | --- |
| id | String | ○ | |
| name | String | ○ | 練習試合など |
| date | String | ○ | 開催日（"YYYY-MM-DD"形式） |
| destinationId | String | ○ | |
| createdAt | Timestamp | ○ | |
| updatedAt | Timestamp | ○ | |

### date

開催日（YYYY-MM-DD）。時刻は保持しない。

### 緯度経度について

Eventは緯度経度を保持しない。`destinationId`経由で`Destination`から取得する
（画面上も目的地選択のみで、緯度経度の個別入力は存在しないため、二重保持を避ける）。

### ホーム一覧の取得方針（イベント数増加への対応）

`events`はチーム運用が続く限り件数が増え続けるコレクションであるため、
ホーム画面（イベント一覧）では全件を一括取得しない。

* 本日以降のイベント（`date >= 本日`）：`date`昇順でクエリし、全件取得する
  （将来予定は件数が少なく保たれるため）
* 過去のイベント（`date < 本日`）：件数のみ集計クエリ（`count()`）で取得して
  「過去のイベント（n件）」に表示し、ドキュメント本体は一覧展開時まで取得しない
* 展開時は`date`降順（新しい順）・20件単位でページ取得し、「もっと見る」で
  追加ページを取得する（04_画面設計.md#5 ホーム（イベント一覧）参照）

# 9. Response（イベント回答）

イベント配下に保存する。

1家庭につき1レコード。**ResponseドキュメントIDをfamilyIdとする**
（`events/{eventId}/responses/{familyId}`）。ドキュメントが存在しない家庭は
「未回答」として扱う（statusフィールドは持たない）。

回答状況（回答済み／一部回答／未回答）の判定方法は本章「選手情報」内の
「回答状況（回答済み／一部回答／未回答）」を参照。

## 家庭情報

| 項目 | 型 | 説明 |
| --- | --- | --- |
| driverOutward | Boolean \| null | 行き車出し。未回答（未選択）ならnull |
| driverReturn | Boolean \| null | 帰り車出し。未回答（未選択）ならnull |
| capacityToday | Number \| null | 当日乗車可能人数（運転者本人を含む総定員）の上書き。通常通り（未変更）ならnull |
| remarks | String | 特記事項（選手個別の特殊ケースもここに集約する） |

### driverOutward・driverReturn

画面上は「未選択（未回答）」「可」「不可」の3状態を取り得るため、`Boolean | null`とする（null=未選択）。
自動保存（#11参照）により、車出しボタンをタップする前に同一家庭の他の項目（乗車可能人数・選手の参加など）が
先に保存された場合でも、未選択の車出しをfalse（不可）として確定させないためにnullを許容する。

### capacityToday

当日の荷物等で車の総定員（`Family.vehicleCapacity`）から変動がある場合のみ数値を設定する。
未変更の場合はnullとする。

## 選手情報

players[]

```json
[
  {
    "playerId": "xxx",
    "isParticipating": true,
    "noOutwardRide": false,
    "noReturnRide": false
  },
  {
    "playerId": "yyy",
    "isParticipating": null,
    "noOutwardRide": true,
    "noReturnRide": true
  }
]
```

| 項目 | 型 | 説明 |
| --- | --- | --- |
| playerId | String | 選手ID |
| isParticipating | Boolean \| null | イベントに参加するかどうか。未選択=null、参加=true、欠席=false |
| noOutwardRide | Boolean | 行きの配車が不要かどうか（現地集合、午後から参加など） |
| noReturnRide | Boolean | 帰りの配車が不要かどうか（保護者迎え、現地解散など） |

### isParticipating

イベント自体に参加するかどうかを表す。画面上は「○／✕／未選択」の3状態があるため、
`Boolean | null`とする（null=未選択）。`false`（欠席）の場合は配車対象外となる。

### noOutwardRide

行きの配車が不要な場合（現地集合など）に `true` とする。

### noReturnRide

帰りの配車が不要な場合（保護者迎えなど）に `true` とする。

### 選手個別の特記事項について

選手ごとの`remarks`は持たない。集合場所変更・同乗者ありなど特殊なケースは、
家庭情報側の`remarks`（家庭備考）にまとめて入力する（画面設計に準拠）。

### 回答状況（回答済み／一部回答／未回答）

家庭単位の回答状況は`status`のような専用フィールドを持たず、以下の項目が
入力済み（null以外）かどうかから**画面側で都度算出する**（04_画面設計.md#7参照）。

判定対象とする項目（対象外の家庭は判定から除外する）：

- `driverOutward` / `driverReturn`（車出し。2つで1つの選択として扱うため、判定上は1項目とみなす）
- 全選手の`players[].isParticipating`（1人でもnullなら、この項目は未回答扱い）
- 全コーチの`coaches[].isParticipating`（本章「コーチ情報」参照。`Coach`が1人以上登録されている家庭のみ判定対象。1人でもnullなら未回答扱い。コーチが1人も登録されていない家庭は対象外）
- 全家族の`familyMembers[].isParticipating`（本章「家族情報」参照。`FamilyMember`が1人以上登録されている家庭のみ判定対象。1人でもnullなら未回答扱い。家族が1人も登録されていない家庭は対象外。`coaches[]`と同じ除外パターン）

`capacityToday`（乗車可能人数の上書き）と`remarks`（備考）は、未入力でも
それぞれ既定値（通常定員・空文字）で成立するため判定対象に含めない。

上記の判定対象項目のうち：

- 全て入力済み → **回答済み**
- 一部のみ入力済み → **一部回答**
- 1つも入力済みでない（Responseドキュメントが存在しない場合を含む） → **未回答**

自動保存（#11参照）は最初の項目変更時点でResponseドキュメント自体は作成するため、
「ドキュメントの存在有無」だけでは回答済みかどうかを正しく判定できない
（例：乗車可能人数だけ変更し、車出し・選手参加が未入力のまま、というケースがあり得る）。
そのため回答状況の判定は常にドキュメントの中身（各項目のnull有無）を見て行う。

## 一時参加者情報

temporaryParticipants[]

```json
[
  {
    "id": "temp-001",
    "name": "山田じいじ",
    "isParticipating": true,
    "noOutwardRide": false,
    "noReturnRide": false
  }
]
```

| 項目 | 型 | 説明 |
| --- | --- | --- |
| id | String | 一時参加者ID。イベント・家庭内で一意な値（追加時に生成） |
| name | String | 名前（自由入力） |
| isParticipating | Boolean | イベントに参加するかどうか。選手・家族と異なり`null`（未選択）を経由しない。追加した時点で常に`true`として作成する |
| noOutwardRide | Boolean | 行きの配車が不要かどうか。追加時は`false`（送迎あり）で作成する |
| noReturnRide | Boolean | 帰りの配車が不要かどうか。追加時は`false`（送迎あり）で作成する |

### FamilyMemberとして登録されない一時的な同乗者

配車画面ではなく、イベント編集 回答入力画面の家庭カードから直接追加する
「今回だけ参加する人」を表すデータである（04_画面設計.md#7参照）。
`FamilyMember`（本章5節）とは異なり、`familyMembers`コレクションには一切保存せず、
このResponseドキュメント内にのみ保持する。イベントを削除すれば、12章の
削除方針（回答・配車結果）に従い自動的に削除される。

追加時、家族として登録して今後も使うかどうかを選択できる。「家族として登録」を
選んだ場合はこの配列には追加せず、代わりに通常の`FamilyMember`を新規作成し、
本章「家族情報」の`familyMembers[]`へ追加する（04_画面設計.md#7参照）。

集合場所は個別に持たず、選手・家族と同じく追加元家庭の`Family.pickupLocationId`を
常に使用する（10章「type: "temporary"について」参照）。

### 回答状況（回答済み／一部回答／未回答）への算入

算入しない。`isParticipating`が`null`を経由せず常に`true`で作成されるため、
判定対象に含めても結果が変わることはない（本章「選手情報」内
「回答状況（回答済み／一部回答／未回答）」の判定対象一覧には一時参加者を含めない）。

# 10. Carpool（配車結果）

イベント配下に保存する。

車ごとに1レコード。

| 項目 | 型 | 必須 | 説明 |
| --- | --- | --- | --- |
| id | String | ○ | |
| direction | Enum | ○ | "OUTWARD"（行き）または "RETURN"（帰り） |
| driverFamilyId | String | ○ | この車を出す家庭のID（運転者個人を特定するデータではない。3章参照） |
| capacity | Number | ○ | 運転者本人を含む総定員 |

同一イベント・同一方向において、1家庭が持つCarpoolは高々1件とする（重複して複数作成しない。12章「例外：車出し可否変更に伴う自動整合」参照）。

### 車名について

`carName`は保持しない。表示に必要な名称は毎回`Family`から生成する。

- 車名：家庭表示名から生成（例：山田 → 山田号）

運転者個人（誰が実際にハンドルを握るか）はデータとして持たない。

## 経由地一覧（集合場所）

経由地一覧はCarpoolのフィールドとして永続化しない。画面表示のたびに以下のルールで動的に算出する。

1. 運転者の集合場所（`driverFamilyId`が属する`Family.pickupLocationId`）を先頭とする
2. 続けて`members`を並び順に走査し、各人の集合場所（種別によらず、所属家庭の`Family.pickupLocationId`。`temporary`は`familyId`が属する家庭の`pickupLocationId`）を、重複を除いて追加する

`members`の変更（ドラッグ＆ドロップによる手動移動を含む）に応じて常に最新の状態が算出されるため、`members`と経由地一覧の不整合は発生しない。

## 乗車メンバー

種別は`player`・`coach`・`family`・`temporary`の4種とする。このうち`temporary`
（一時参加者）のみマスタに存在せず、9章「一時参加者情報」のデータを参照する。
コーチ・家族・一時参加者は「運転しているかどうか」に関わらず、選手と同格の
通常の乗車メンバーとして扱う。「運転コーチ」「運転家族」という特別な概念は
持たない（運転者個人を特定するデータは持たない）。
`player`は`playerId`、`coach`は`coachId`（＋`Coach.name`）、`family`は`familyMemberId`
（＋`FamilyMember.name`）、`temporary`は`familyId`＋`temporaryParticipantId`
（＋Response.temporaryParticipants[]の`name`）で表現する。

```json
[
  { "type": "player", "playerId": "xxx" },
  { "type": "coach", "coachId": "zzz" },
  { "type": "family", "familyMemberId": "yyy" },
  { "type": "temporary", "familyId": "family-003", "temporaryParticipantId": "temp-001" }
]
```

### type: "player" について

`direction = OUTWARD`の場合は`Response.players[].isParticipating`が`true`かつ
`noOutwardRide`が`false`の選手が対象。`direction = RETURN`の場合は同様に
`isParticipating`が`true`かつ`noReturnRide`が`false`の選手が対象。

### type: "coach" について

`direction = OUTWARD`の場合は`Response.coaches[]`のうち`isParticipating`が`true`かつ
`noOutwardRide`が`false`のコーチが対象。`direction = RETURN`の場合は同様に
`isParticipating`が`true`かつ`noReturnRide`が`false`のコーチが対象。

対象方向の車出し可否（`driverOutward`/`driverReturn`）に関わらず、上記条件を
満たすコーチは（1家庭に複数人いる場合は該当する全員を）常にmembersに含める。
車出しが可の場合は自分の家庭の車のmembersに、車出しが不可の場合は所属家庭の
選手と同じ集合場所から乗客として自動配車の対象になる（07_配車アルゴリズム.md参照）。

### type: "family" について

`direction = OUTWARD`の場合は`Response.familyMembers[].isParticipating`が`true`かつ
`noOutwardRide`が`false`の家族が対象。`direction = RETURN`の場合は同様に
`isParticipating`が`true`かつ`noReturnRide`が`false`の家族が対象。

判定ロジックは`type: "player"`と全く同じであり、家庭の車出し可否
（`driverOutward`/`driverReturn`）に紐づく特別な扱い（`type: "coach"`のような
「車出しが可なら自分の家庭の車、不可なら乗客」という分岐）は行わない。
自動配車アルゴリズムが選手と同じ枠組みで配車先の車両を決定する
（07_配車アルゴリズム.md参照）。

### type: "temporary" について

`direction = OUTWARD`の場合は対象家庭のResponse.temporaryParticipants[]のうち
`isParticipating`が`true`かつ`noOutwardRide`が`false`の一時参加者が対象。
`direction = RETURN`の場合は同様に`isParticipating`が`true`かつ`noReturnRide`が
`false`の一時参加者が対象。判定ロジックは`type: "family"`と全く同じである。

他の3種と異なり、名前をマスタ（`players`・`coaches`・`familyMembers`）から
解決しない。`familyId`が属する家庭のResponseドキュメント
（`events/{eventId}/responses/{familyId}`）内の`temporaryParticipants[]`から、
`temporaryParticipantId`が一致する要素の`name`を直接参照する
（9章「一時参加者情報」参照）。

集合場所は他の3種と同じく、`familyId`が属する`Family.pickupLocationId`を
参照する（個別の集合場所は持たない）。

# 12. 削除方針

削除方針はデータの種類ごとに異なる。

## 家庭・選手・コーチ・家族

用途に応じて論理削除・物理削除を使い分ける。

### 卒団・対象外になった場合（論理削除）

家庭・選手・コーチ・家族が卒団（コーチ・家族の場合は対象外になること）した場合は、`isActive`を`false`にして非表示とする。

- 新規イベントの回答画面・配車画面には表示しない
- 過去のイベント履歴（Response・Carpool）は引き続き参照・表示できる

### 登録ミスの取り消し等（物理削除）

管理者は、通常運用の機能として家庭・選手・コーチ・家族を物理削除できる（04_画面設計.md#10 登録情報）。

- 過去の回答（Response）・配車結果（Carpool）から参照中であっても削除を禁止しない（参照有無のチェックは行わない。集合場所・目的地と同じ考え方）
- 削除前に確認ダイアログで警告する（04_画面設計.md#10）
- 削除後の復元手段は用意しない
- 家庭を削除した場合、その家庭に属する選手・コーチ・家族も道連れで物理削除する
- 削除の結果、過去の回答・配車結果が存在しない選手・コーチ・家族・家庭を参照する状態（参照切れ）が発生し得ることを許容する
  - 配車結果画面の乗車メンバー表示・車名表示に限り、「（削除済み）」と分かる最低限の表示を行う（04_画面設計.md#8）
  - 上記以外の画面は当面対応しない
  - 参照切れ状態の自動修復・一括置換などの機能は設けない（運用でカバーする）

## イベント

管理者は、通常運用の機能としてイベントを物理削除できる（04_画面設計.md#12 イベント情報編集）。

- 削除対象は対象イベント自身と、配下の回答（Response）・配車結果（Carpool、行き・帰り両方向）
- 削除前に確認ダイアログで警告する（04_画面設計.md#12）
- 削除後の復元手段は用意しない

## 集合場所・目的地

管理者は、通常運用の機能として集合場所・目的地を物理削除できる（04_画面設計.md#10 登録情報）。

- 家庭（`Family.pickupLocationId`）・イベント（`Event.destinationId`）から参照中であっても削除を禁止しない（参照有無のチェックは行わない）
- 削除前に確認ダイアログで警告する（04_画面設計.md#10）
- 削除の結果、`Family.pickupLocationId`・`Event.destinationId`が存在しないドキュメントを指す状態（参照切れ）が発生し得ることを許容する
  - ホームのイベント一覧・配車画面の経由地表示に限り、「（削除済み）」等と分かる最低限の表示を行う（04_画面設計.md#5、04_画面設計.md#8）
  - 上記以外の画面（イベント情報編集・イベント作成の目的地選択、家庭編集画面の集合場所選択等）は当面対応しない
  - 参照切れ状態の自動修復・一括置換などの機能は設けない（運用でカバーする）

## 回答・配車結果

回答・配車結果は単独では物理削除しない。イベントを削除した場合のみ、そのイベント配下の回答・配車結果が道連れで削除される（前述「イベント」参照）。

一時参加者（9章「一時参加者情報」）はResponseドキュメントの一部として保存するため、専用の削除ルールは設けない。上記の回答削除に伴い自動的に削除される。

一時参加者を個別に取り消す（04_画面設計.md#7 一時参加者の追加の×ボタン）操作は、マスタを持たないためこの一時参加者に限り物理削除に相当する。取り消し後もCarpool.membersに`type: "temporary"`の参照が残っている場合（配車画面を開く前など）は、前述「登録ミスの取り消し等（物理削除）」の家庭・選手・家族と同様、配車結果画面の乗車メンバー表示に限り「（削除済み）」と分かる最低限の表示を行う（04_画面設計.md#8）。

## 例外：開発用「サンプルデータ投入」機能

登録情報画面の開発用機能「サンプルデータ投入」（開発環境限定。本番環境では利用不可）に限り、
上記の削除方針の例外として、確認ダイアログなしでイベント（配下の回答・配車結果を含む）を一括物理削除してよい。

- 対象は集合場所・目的地・家庭・選手・家族・イベント（配下の回答・配車結果を含む）。このうち集合場所・目的地・家庭・選手・家族は通常運用でも物理削除可能だが、本機能は一括リセット目的のため個別の確認ダイアログを表示しない点が例外
- 本機能は開発環境での評価・動作確認を目的とした一括リセット用であり、
  過去のイベント履歴が家庭・選手・家族を参照する整合性は保証しない

## 例外：配車再作成

イベント編集 回答入力画面（04_画面設計.md#7）の「自動配車」から配車を再作成する場合に限り、
上記の削除方針の例外として、対象イベント配下の配車結果（Carpool）を物理削除してよい。

- 再作成確認ダイアログ（04_画面設計.md#7 配車再作成）で「再作成」が選択された場合のみ実行する
- 削除対象は対象イベント配下の配車結果（行き・帰り両方向）のみとし、家庭・選手・イベント・回答は削除しない
- 削除後、最新の回答内容を基に配車を再作成する（再作成前の配車結果の履歴は保持しない）

## 例外：行き⇔帰りコピー

配車画面（メイン）の「⋮」メニューから行き⇔帰りコピー（04_画面設計.md#8 行き⇔帰りコピー）を実行する場合に限り、上記の削除方針の例外として、コピー先方向の配車結果（Carpool）を物理削除してよい。

- 確認ダイアログ（04_画面設計.md#8 行き⇔帰りコピー）で「コピー」が選択された場合のみ実行する
- 削除対象はコピー先方向の配車結果のみとし、コピー元方向・家庭・選手・イベント・回答は削除しない
- 削除後、コピー元方向の配車結果を基にコピー先方向の配車結果を再作成する（コピー元の車の運転者家庭がコピー先方向で車出し不可の場合はその車を作成しない。コピー元のメンバーのうちコピー先方向で対象外になる人は含めない）
- 再作成後、対象外になった乗車メンバーの除去・車出し可否の変更に応じた車の自動追加（前述「例外：車出し可否変更に伴う自動整合」）と同じ処理をコピー先方向に適用し、コピー先方向で車出し可能なのにコピー元に車がなかった家庭の空車を補完する

## 例外：車出し可否変更に伴う自動整合

配車画面を開いたタイミングで、回答編集画面での車出し可否（driverOutward/driverReturn）の変更を検知した場合に限り、上記の削除方針の例外として、対象家庭・対象方向のCarpoolを物理削除してよい（04_画面設計.md#8 画面を開いた際の自動整合）。

- 対象は、車出し可否がtrueからfalseに変わった家庭の、該当方向のCarpoolのみとする
- 確認ダイアログは表示せず、配車画面を開くたびに自動的に反映する
- 削除により当該Carpoolの乗車メンバーは未配車として扱われる（他の車・他のメンバーの配置には影響しない）
- 逆に、車出し可否がfalseからtrueに変わった家庭について該当方向のCarpoolが存在しない場合は、新規にCarpoolを作成する（乗車メンバーなし、定員は`capacityToday`。未設定の場合は`Family.vehicleCapacity`）。同一家庭・同一方向のCarpoolが既に存在する場合は作成しない

## 例外：開発用「サンプル回答生成」機能

イベント編集 回答入力画面の開発用機能「サンプル回答生成」（04_画面設計.md#7 開発用機能。
開発環境限定。本番環境では利用不可）に限り、上記の削除方針の例外として、
対象イベント配下の回答（Response）を物理削除してよい。

- 確認ダイアログで実行が選択された場合のみ実行する
- 削除対象は対象イベント配下の回答（Response）のみとし、家庭・選手・家族・イベント・配車結果は削除しない
- 削除後、登録済みの家庭・選手・家族等のマスタデータを基にランダムな回答を生成・登録する
