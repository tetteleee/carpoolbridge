# コーチ別エンティティ化・複数コーチ対応 引き継ぎ資料

作成日: 2026-07-31
更新日: 2026-07-31
ステータス: **設計書改訂済み・実装未着手**（5章の論点は人間承認済み。次は7章「次にやるべきこと」3.のタスク分割）

## 1. 経緯

「マスタ管理画面で家庭・選手・家族を削除できるようにする」実装
（`docs/05_データ設計.md#12` 削除方針改訂）の作業中に、以下の提案が挙がった。

> コーチも、選手や家族と同じようにデフォルトで枠なし、必要な時に＋ボタンで追加するようにした方が良さそう

この提案について人間へ質問し、方針の一部は決まったが、影響範囲の大きい論点（5章）が

本提案は着手前の状態でこの資料に引き継ぐ。

## 2. 現状（変更前）の仕様

- `Family.coachName`: `String | null`。1家庭につき1つの文字列項目としてコーチ名を保持する
  （`05_データ設計.md#3`）。選手・家族のような独立ドキュメント（Player/FamilyMember）ではない
- 家庭編集画面（`04_画面設計.md#10.4`）では、コーチ欄は未登録でも常に1つのボックスとして
  表示される（選手・家族は0人なら何も表示せず「＋」で追加する形式であり、非対称）
- `Response`（`05_データ設計.md#8`）では、`coachParticipating`/`coachNoOutwardRide`/
  `coachNoReturnRide`という単一の項目としてコーチの回答を持つ（`players[]`のような配列ではない）
- `Carpool.members`（`05_データ設計.md#10`）の`type: "coach"`は`familyId`のみで識別する
  （表示のたびに`Family.coachName`を参照する）。1家庭1コーチ前提の設計

## 3. 提案の要点

1. 家庭編集画面のコーチ欄を、選手・家族と同じ「デフォルト非表示・＋ボタンで追加」の見た目に変更する
2. 1家庭に複数のコーチを登録できるようにする

## 4. 決定事項（人間への質問・回答結果）

| 論点 | 結論 |
|---|---|
| コーチの持たせ方 | 選手・家族と同じ別エンティティにする（`Coach`コレクションを新設し、`id`・`isActive`等を持たせる） |
| 複数コーチ | 許可する（1家庭に複数人登録可） |
| 回答（Response）・配車結果（Carpool）側のコーチの持たせ方 | **未確定。5章参照** |
| 進め方 | 削除機能を先に仕上げ、本提案は別タスクとする（今回はここまで） |

## 5. 未確定の論点（最優先で人間の最終判断が必要）

複数コーチを許可した場合、`Response`・`Carpool`側のコーチの持たせ方を変えるかどうかが未確定。

**論点**: `Family`に複数コーチを登録できるようにしたにもかかわらず、`coachParticipating`等が
単一項目のままだと、コーチが2人いる家庭で「Aさんは参加するがBさんは欠席」のような回答自体が
表現できない（マスタ側と運用側でデータモデルが矛盾する）。

| | 変えない（単一項目のまま） | 選手と同じ配列構造に変える |
|---|---|---|
| メリット | 改修範囲が家庭編集画面だけで済む | マスタ（複数人可）と回答・配車のデータモデルに矛盾がなくなる。現状すでに選手・家族と“ほぼ同じだが微妙に違う”コーチ専用コードが各所にあるものを統一でき、結果的にシンプルになる |
| デメリット | 複数コーチ登録を許可した意味がなくなる（結局1人分しか回答できない） | 影響範囲が広い（6章参照） |

**決定（2026-07-31 人間承認済み）**: 配列構造に変える。複数コーチ登録を許可した時点で、
単一項目のままでは機能として成立しないため。

併せて、配列化に伴い新たに生じた以下の派生論点も人間へ確認し、承認を得た。

| 論点 | 結論 |
|---|---|
| 05_データ設計.md#3「コーチが運転する場合はcoachNameをそのまま表示する」特例（運転者がコーチの場合のみ本人名を表示）の扱い | 特例を廃止し、家族（FamilyMember）が運転する場合と同じ扱い（家庭表示名を使用）に統一する。コーチが複数人になると「どのコーチの名前を表示するか」を特定する手段がないため |

6章に基づき設計書（`02_要件定義.md`・`03_ユースケース.md`・`04_画面設計.md`・`05_データ設計.md`）を改訂済み。
`06_認証・権限管理設計.md`のFirestore Security Rulesは`coaches`コレクションを
既に見込んで実装済みのため変更不要。`07_配車アルゴリズム.md`はコーチの人数を
前提としない汎用的な記述のため変更不要（と判断した）。

次は7章「次にやるべきこと」3.のとおり、`docs/50_タスク作成ルール.md`に従い
`tasks/`へタスクファイルを分割作成する工程に進む。
